# Project-qualified roles govern Portal access

Use Zitadel roles in the configured project to authorize both kinds of Portal access. A person needs the `hub-admin` role for the browser UI; a machine account needs `publisher` for the bearer API. Each role name can be overridden in Portal config, with those names as defaults. A grant in any authorization organization counts if it belongs to the configured project. This replaces the browser owner-email checks and the machine API's organization-specific check. We accept the broader reach of cross-organization grants in exchange for one project-level policy without per-person lists or an authorization organization setting. The two roles do not imply each other.

Browser sessions still require Zitadel sign-in, but a session alone does not grant Portal access. oauth2-proxy retains and refreshes the browser access token in an encrypted, signed cookie so the browser can keep a 12-hour cookie without a new session service. Refresh can reset that cookie's expiry, so this is a sliding limit, not a hard 12-hour maximum.

nginx passes the token from the auth subrequest to the Portal, which introspects it with the existing `hub-api` credentials and checks token activity, the signed-in subject, and the project-qualified administrator role. The Portal caches this check for at most 60 seconds. After the cache expires, an unavailable Zitadel blocks access rather than preserving a stale grant. Portal introspection failures return `503`; if oauth2-proxy cannot refresh the token first, it may instead treat the session as unauthenticated and send the browser to sign-in. Zitadel's propagation delay remains additional to the cache duration. nginx relays refreshed cookies, including a second split-cookie part. If cookie storage proves unreliable, reconsider server-side session storage.

Grant the roles before removing the old checks; obsolete authorization organization and owner-email settings must fail startup rather than silently stop protecting access. We do not require a live Zitadel compatibility check before migration; if the deployed issuer omits the required claims, the Portal fails closed instead of falling back to email or token activity. The two API prefixes and machine PAT transport from ADR 0004 remain unchanged.
